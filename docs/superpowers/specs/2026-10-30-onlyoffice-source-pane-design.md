# ONLYOFFICE 替换详情左侧原文区

状态：待确认的接入设计；未开始修改产品代码。+
## 意图与已确认选择

用户希望在当前 RFQ 系统中嵌入 ONLYOFFICE，用真实 Word/PDF 完成标注批阅。用户已选择“直接替换详情左侧原文区”，并要求新建分支。当前分支为 `codex/onlyoffice-source-pane`，沿用当前工作区，保留已有未提交的界面改动。

本轮交付是本机可验证的文档集成，覆盖上传、打开、人工批阅、保存回调、刷新重开和下载。社区版授权讨论不阻止本机接入验证；本轮不对外发布或联系销售。

## 现状与约束

- `rfq-react-prototype` 使用 React 19、Vite、Ant Design，业务状态及演示身份保存在浏览器。详情由 `ResponsePage` 的左右两栏组成，左侧 `SourceDocumentPane` 展示条款摘录、应用批注及模拟 Word 排版。
- `SourceUploadDialog` 通过 `uploadMetadata` 丢弃文件二进制；当前上传、解析均是模拟流程。历史元数据不能恢复出原始 Word。
- `rfq-service` 为 Spring Boot 3.5.9 / Java 17 独立后端，目前只有框架与健康接口，没有文件存储、业务账号或认证。
- 本机已有 OTHER 项目的 ONLYOFFICE 9.3.1 服务，`http://127.0.0.1:8081/healthcheck` 返回 `true`。不修改其配置、容器或数据。接入配置允许连接已有服务；也提供 RFQ 独立服务的可选启动配置。
- 2026-10-30 当前前端基线为 327 项测试通过。已有工作区改动属于任务起点，后续修改须在其基础上进行，禁止覆盖或重置。

## 接入方式比较

1. 新增独立“原文件批阅”大幅编辑入口：完整工具栏空间充足，对现有摘录影响小，但阅读与应答需要切换上下文。
2. 直接替换详情左侧原文区：原文件与应答保持并排，符合用户已选方式；需要调整窄栏工具栏、编辑器生命周期及缺少原件的状态。

采用方式 2。以下未由用户指定的实现细节为建议，待设计确认。

## 页面行为

- 详情左侧主要区域改为真实 ONLYOFFICE 编辑器，右侧继续使用现有基本信息、应答澄清及协作记录。沿用可拖动分栏；提供放大编辑区的操作，便于使用编辑器工具栏。
- 有真实文件的 DOCX/PDF 直接打开。首次先覆盖 DOCX 与 PDF；旧 DOC 可在验证转换与保存后开放，无法编辑的格式显示明确说明，不冒充成功打开。
- 新上传文件通过后端保存真实二进制，然后在浏览器文件记录中保存服务端文档引用，不把 File、Blob 或 Base64 放进 localStorage。
- 旧记录或示例没有真实原件时，左侧明确显示“尚未关联原文件”。有来源管理权限的 SR 可上传对应原件；其他人显示只读说明。已存在的条款摘录仍可通过辅助入口查看，以便继续处理现有项目。
- 原件上传后保留不可变原始文件，批注、修订及编辑写入单独的批阅副本；下载时区分原件与批阅版。页面明确显示正在查看批阅副本。
- 文档标题、加载、连接失败、重试、服务端保存时间等状态位于左侧。编辑器显示修改状态不等于文件已经写回 RFQ 后端；只有收到成功保存回调后显示“已保存”。关闭或切换时对尚未落盘的改动给出提示。
- 保存和下载属于文档批阅操作，不计作既有流程的“正式对外应答导出”，也不自动通过任何条款确认或最终评审。

## 权限与本轮边界

- 延续 `source:manage`：仅具备项目来源管理权限的 SR 可上传原件及修改批阅副本；其余能够访问项目的身份只读查看文件。编辑器配置在服务端签名。
- 现有系统没有服务端企业身份；本轮仍是本机演示，不能把前端演示身份描述为生产级鉴权。文档 API 使用随机文档访问凭据，文件下载使用有时限的签名地址，避免裸露存储路径。企业认证与服务端项目成员授权留待正式后端接入。
- 现有应用批注、应答建议及条款定位使用条款 ID 与文本区间，和 ONLYOFFICE 内部定位机制不同。本轮不伪造双向同步，不把旧应用批注自动写入原文件。
- 选择右侧条款仍切换业务数据；首版不承诺自动滚动 ONLYOFFICE 到对应原文位置。历史条款摘录保留辅助查看方式。
- 修改批阅副本不覆盖已抽取要求，也不使旧确认自动适用于新原件。上传不同客户版本沿用新来源版本流程；全文重新解析及条款比对继续明确为现有模拟功能。
- AI 自动写批注、Automation API、原文与业务条款双向同步、多人权限及正式对外文档生成不在本轮范围。

## 前后端与文档服务链路

1. 浏览器将真实文件提交至 `rfq-service`；后端校验扩展名、基础文件格式、文件大小及来源引用，生成随机存储 ID，持久化原件、批阅副本与元数据。
2. 前端按当前文档引用请求编辑器会话配置。后端生成 ONLYOFFICE 所需的文档 key、下载地址、保存回调地址、权限和 JWT，前端只获取签名后的配置，永不获得 JWT 共享密钥。
3. 前端加载配置指定服务的官方 Docs API，在左侧容器挂载 `DocsAPI.DocEditor`。切换文件、身份、项目或卸载组件时销毁旧实例，并取消旧请求，防止后返回的响应覆盖当前文件。
4. ONLYOFFICE 通过可达的后端地址下载批阅副本。浏览器访问地址与 Docker 服务间地址分开配置，避免容器把 `localhost` 当作宿主机。
5. 后端校验保存回调 JWT、文档 key 与当前会话；仅处理成功保存状态 2、6，错误状态保留已有版本并记录失败。成功下载文件后原子替换批阅副本，持久化保存时间与版本信息，按 ONLYOFFICE 约定返回 `{"error":0}`。
6. 文件下载仅允许配置的文档服务来源，限制重定向、超时和大小，防止借保存回调下载任意地址。同一文档保存串行处理；重复回调幂等，过期会话不能覆盖新版本。
7. 强制保存状态 6 不提前变更正在协作的文档 key；最终保存完成后按官方规则更新后续会话 key。前端通过查询文档状态确认落盘，刷新后重新获取最新配置。

API 具体命名由实现者决定，最少提供：服务状态、文件上传、编辑器配置、签名内容下载、保存回调、文档保存状态，以及原件/批阅版下载。普通接口沿用 `{code,msg,data}`；保存回调必须使用 ONLYOFFICE 的协议格式。

## 部署与持久化

- 为 `rfq-service` 新增 ONLYOFFICE 配置：浏览器可见地址、后端可见的服务地址、文档服务可达的回调基地址、共享 JWT 密钥、文件目录及上传上限。
- 本地文件写入任务专用目录并加入忽略规则；服务重启后恢复元数据与文档，不能仅存在进程内 Map。密钥放入已忽略的环境配置，不写入提交、日志或网页。
- Vite 使用同源代理连接后端。保持默认服务本机可用；不向外网部署。
- 如果复用现有文档服务，只读取所需配置并调用官方接口，不变更其服务配置。若需独立 RFQ 文档服务，则使用独立容器、端口和持久卷，避免影响已有项目。

## 验收

- 单元/后端集成：文件类型与大小、真实文件持久化及重启恢复、JWT 配置/回调验签、非法及过期 key、状态 2/6、重复回调、失败时保留旧文件、回调地址限制。
- 前端：服务不可用/重试、缺少原件、只读身份、文件与项目切换、编辑器销毁、已保存状态来源以及原有存储兼容。
- 浏览器：上传真实 DOCX，左侧打开，添加批注及修订，保存、关闭、刷新重开并下载；检查 DOCX 内仍包含原生批注/修订结构。PDF 完成打开、至少一种标注、保存、重开与下载验证。
- 回归：现有前端测试、生产构建、后端完整测试；实际检查右侧应答编辑、身份切换、历史摘录入口、分栏与窄屏。
