# Word/PDF 统一批注接入 RFQ 项目

## 用户确认

- 将已经确认的 WordCraft/PdfCraft Demo 接入项目，在新分支开发。
- 延续先前选择：详情左侧显示真实原文，右侧继续处理应答与协作记录。
- 文件批注及回复与右侧协作记录双向同步。
- 批注必须关联条款才进入协作记录；未关联的原文件批注保留在文件中，提示选择条款后同步。

## 工程现状和实施选择

工作分支 `codex/rfq-craft-document-review` 从已完成 Demo 创建，并合入此前
`codex/onlyoffice-source-pane` 的上传、版本存储、条款联动和导航保护代码。
以下具体架构为实施选择，沿用 React 19、Vite、Spring Boot 和固定版本的原生编辑器。

1. 使用原生编辑器 iframe 加已经确认的共用 DOM 批注界面。React 负责项目、条款、权限和保存。
   完整 Demo 页面含独立文件切换和下载流程，会与项目操作重复，因此不直接嵌入整个 Demo。
2. 编辑器静态资源与项目同源发布，开发和构建准备时从本项目的固定版本构建产物复制，
   不依赖 18771 Demo 服务或 ONLYOFFICE 服务。
3. 新文件接口使用 `/api/craft`，复用已有格式验证、不可变原件、分版本批阅副本和随机访问凭据。
   保存必须带当前 revision，冲突返回 409；失败保持原件和此前批阅版本。
4. 已上传的 ONLYOFFICE 文件引用继续保留。首次接入时读取旧服务的原件及最近批阅版，
   导入独立的 Craft 存储，导入失败不覆盖旧引用。开发环境使用独立后端端口及存储，
   避免和已有分支服务互相覆盖文件。

## 原文和条款联动

- 按项目、来源文件、来源版本绑定编辑器；切换条款不重建同一文件的编辑器。
- 右侧选条款时在原生文本中定位；唯一匹配才声明精确定位，多处匹配或缺失明确提示。
  PDF 可以按来源页码定位，但不能把页码跳转宣称为文本精确匹配。
- 原文选中已匹配的条款时，右侧跟随切换；右侧未保存业务内容继续受现有离开保护约束。
- 暂无原件和历史版本保留条款摘录；不通过换文件重置现有业务数据。

## 双向同步

- 记录绑定为来源三元组、服务端文档 ID、原生稳定 comment key。PDF 不把易变数组下标当身份。
- 原生快照提供批注内容、作者、引用原文、条款 ID、回复、解决状态和稳定 key。
- 原文件新增、修改、回复、解决/重开、删除反映到同条款协作记录。删除不删除已关联评审事项，
  对业务记录保留删除标记以避免刷新后复活。
- 右侧新增、编辑、回复和解决反向调用白名单原生命令，真实写入 DOCX/PDF 批注结构。
  不使用绘制的假批注代替文件批注。无匹配锚点时保留业务记录并明确显示待关联/同步状态。
- 未关联条款的原生批注显示待关联入口；用户选择来源版本内的条款后才进入协作记录。
- 保留作者、时间、@成员和关联事项；同步不替换这些业务字段，不重复创建回复，不形成回传循环。
- 已接收快照、正在提交的原生命令和业务状态要按文档代次及请求序号协调，防止旧响应串到新文件。
- 业务记录沿用现有浏览器存储。文件保存到后端后才标为文件已保存；失败和冲突保留本地修改，
  刷新时待同步业务修改可重放，不能因服务端文件较旧而静默删除业务讨论。

## 权限和保存

- 原文编辑、上传沿用来源管理权限；批注沿用条款处理权限和作者限制。
- 只读/过期来源在原生编辑器及宿主命令层均禁止修改，不能只隐藏网页按钮。
- 保存流程是原生提交草稿、返回文件字节、后端校验并原子发布新 revision、确认成功。
  保存期间继续输入不会被此前保存响应标成已落盘；切换/离开时继续提示未保存修改。
- 不改变条款确认、任务、评审和正式导出规则。身份仍是既有本机模拟，不声称企业级服务端鉴权。

## 验收与边界

- 前端全套测试和生产构建；新增来源隔离、同步幂等、回复去重、作者限制、旧响应及保存冲突回归。
- 后端上传、导入、原件不变、保存重开、无效访问凭据、非法格式、超限及 revision 并发测试。
- 原生编辑器测试验证锚点定位、只读/批注权限和双向 upsert 实际进入文件；编译 WASM。
- 当前浏览器自动化未开放，不绕过设置；通过 DOM、原生引擎、文件字节及 HTTP 验证，报告视觉验收限制。
