# 条款确认历史实施计划

> **For agentic workers:** Use superpowers:executing-plans and test-driven development. Track each task with checkboxes.

**目标**　应答卡片可以对比已确认版本，并将旧内容恢复为当前条款草稿。

**设计依据**　[RFQ 应答版本与草稿流程设计](../../product/RFQ应答版本与草稿流程设计.docx)及本次会话中的确认历史抽屉方案。

**范围**　条款应答的确认、历史查询和恢复。沿用项目授权、应答编辑权限、当前确认人校验及来源校验。现有应答修订号继续用于乐观锁，确认版本独立编号。

## 任务一 数据库与接口

- [ ] 在 `ResponseHistoryIntegrationTest` 中验证确认、改派、恢复、草稿检查点及重新确认。观察未实现接口的失败。
- [ ] 新增 V9 历史表。通过 `ResponseController` 提供 `GET /history` 和 `POST /restore`。历史按条款隔离，区分确认版本与草稿检查点。
- [ ] 在 `ResponseService` 的现有写入事务内生成确认快照、保存检查点或恢复应答字段。遇到可核实的旧确认内容时，以原编号建立历史起点。
- [ ] 运行应答、改派和确认历史测试。验证越权和过期请求、来源变更、确认内容相同时的编号，以及 A、B、C 的恢复记录。

## 任务二 应答卡片

- [ ] 验证应答客户端传递来源版本、应答修订号和历史条目选择，并在有修改时通过一次请求保存并确认。
- [ ] 在 `ResponsePage` 的应答卡片标题旁加入「确认历史」。抽屉显示版本、人员、时间和字段差异。恢复操作确认后回到原条款，显示恢复来源和待确认状态。
- [ ] 用真实页面或浏览器回归核对查看、恢复、待确认及再次确认，运行前端测试和构建。
